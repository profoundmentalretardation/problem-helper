A student never talks to us. We read their failing code, prove a fix on the real judge, and hand back one hint.

A frontend posts user_id + problem_id. Everything after that runs in a worker, checkpointed step by step, with every model call priced and logged.

Pick a scenario below to trace a request through the pipeline, or open any step for what it actually does and what it must never do.

    02 — Outcomes

    Six ways a request ends

    The split that matters is we chose to stop versus our infrastructure broke. Collapsing them would report an internal fault for a request handled exactly as designed — and poison the analytics.

    StatusMeaningReason codesWhose call

    03 — Resume

    What a crash costs

    Resume is step-level. Drag the checkpoint to the last step that finished before the crash, and the pipeline above annotates itself: what is skipped, what is reloaded from the store instead of re-derived, and what actually runs again.

    resume_step NULL — fresh request
    skipped reloaded from the store runs
    > Resume view is off. The pipeline shows a fresh request.
    A checkpoint is only worth writing if the step’s output is readable back. Loop 1’s verified code and run id are persisted before its checkpoint; the hint checkpoint moved to after the row is inserted. A checkpoint past a step whose output is missing is treated as a corrupt row and failed once with the real reason — never as a licence to re-run the step, because the reclaim loop would do that up to maxClaimAttempts times, re-spending both model budgets and re-submitting to the judge each cycle.

    04 — Loop 1

    Repair, verified on the real judge

    The model has no native tool-calling channel here — llm.ChatClient only exchanges schema-validated JSON, so the three tools are a discriminated action field on one response schema.

    Verification is the judge’s own accept verdict, not just the baseline tests. This course’s ejudge runs acm scoring, which halts at the first failure, so a student’s failing run only has results up to that point. Code passing exactly those and failing a later test would otherwise ship as a “verified fix”.

    05 — Loop 2

    Hint, then a guardrail that can only say yes

    The hard part is rejecting hints, not writing them. Cheap deterministic rules run before any model call; the guardrail must be a different model family than the writer, enforced at startup.

    Gate on the irreversible act

    Approval gates delivering a hint, not writing one. A checker failure is never approval, and neither is prose, the wrong schema, or a reply whose types are wrong.

    An interruption is not a verdict

    An unreadable answer fails closed. A cancelled context or a dead connection is not an answer at all — treating it as guardrail_failed threw away the retry budget and terminated a request that should have stayed reclaimable.

    Always append a turn before retrying

    llm.Chat’s own schema retry runs on a private copy of the conversation, so a bare continue resends a byte-identical message list — the model repeats itself and every retry burns two billed calls on the same exchange.

    06 — Queue

    Claim, heartbeat, reclaim

    Two workers running the same request means two judge submissions under one shared system login and both model budgets spent twice. Ownership is therefore enforced in SQL, on every write.

    Every mid-run write is claim-scoped

    SetResumeStep, SetRepairResult, SetBestSubmission, SetHintID, SetFailureReason, SetError — not just the terminal transition. An unclaimed row is not writable either: that is exactly the post-reclaim, pre-claim window in which the stale worker is most likely still executing steps.

    The judge has no fence token of ours

    SQL cannot refuse a submission that already happened, so loop 1 re-asserts the claim in the round trip immediately before SubmitAsSystem. A guard error aborts too — it is not evidence the claim is intact.

    Reclaim uses the database clock

    heartbeat_at is always written by now() on the server. A cutoff computed in Go made reclaim depend on clock drift: too fast and live rows get reclaimed mid-submit, too slow and nothing is ever reclaimed at all.

    Bounded by claim_attempts

    A pipeline that errors deterministically would be handed out forever. Past the cap the row moves to failed with the reason recorded, instead of back to pending.

    07 — Metaloop

    Mistakes become the next prompt

    Off the critical path. It sweeps at startup and then on an interval — a bare 24h ticker meant a service redeployed daily never ran the curator at all.

    A sweep that wrote anything seals its batch — even when it gives up or errors. Merges commit as they go, so leaving the batch open makes every later sweep re-send it and merge again, inflating mistakes.count without bound. Only a sweep that wrote nothing leaves the batch for a retry. The sealing write runs on a detached context, because the likeliest way to reach it is the context dying.

    09 — Operating

    Surface, spend, configuration

    RouteAuthNotes
    POST /helpAPI_TOKENEnqueues and returns request_id. Rate-limited per user per day, counted inside a transaction holding an advisory lock — the “obvious” single-statement version passes every racer.
    GET /requests/{id}API_TOKENStatus, hint when done, fixed message when failed.
    GET /admin/requestsADMIN_TOKENFilter by useless / status / model; full error text.
    POST /admin/requests/{id}/uselessADMIN_TOKENEffectiveness labelling.
    POST /admin/metaloop/runADMIN_TOKENRuns a sweep on a detached context and extends its own write deadline — 30 minutes against a 30-second WriteTimeout.

    Two caps, two enforcement points

    • max_cost_per_loop — checked before each attempt starts
    • max_cost_per_retry — checked against one attempt’s spend
    • Both can overshoot by at most one call: a call’s cost is only known after it returns
    • What a cap is charged is what llm.Chat spent — a schema-rejected exchange billed two calls, and both count

    Fail-open keys are startup errors

    • Zero cost caps read as “unlimited”; zero max_retries returns without calling a model
    • A pricing entry missing output prices every output token at zero
    • n_submissions: 0 removes the scrape cap; daily_requests_per_user: 0 429s everyone
    • All of it is validated by config.Load, before traffic

    Different family, enforced

    The guardrail’s model family is compared against the hint writer’s at startup, on the id’s last path segment up to its first -, so a routing prefix cannot disguise one model as two.

    Shutdown needs two budgets

    A metaloop handler may legitimately hold its connection for 30 minutes, so one shared budget let HTTP shutdown eat all of it and abandoned every in-flight pipeline. pgxpool.Close is not a defer: it closes only once the workers actually drained.
