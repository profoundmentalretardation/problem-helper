## Как устроен пакет `memory/`

Четыре стора, каждый держит то, что ему подходит:

```
memory/
  db.py       пути к state/ и connect()          ← общий, 20 строк
  sql.py      SQLite: submissions, repairs, hints         ← A
  rules.py    markdown-правила + сборка push-контекста     ← A
  docs.py     документный стор: факты с cue, скоупы        ← B
  events.py   append-only лог с hash-chain + handoffs      ← B
  notes.py    shared-заметки студентов + конверт           ← C
```

Правило, что куда: если два цикла по этому **фильтруют** — это строка в SQLite; если один агент
написал это прозой для другого — это документ; если это должно быть верно на **каждом** ране —
это markdown.

Каждый модуль делает свой `CREATE TABLE IF NOT EXISTS` при первом обращении, общей миграции нет.
Модули импортируются напрямую (`from memory import docs, events`), а не реэкспортом, — поэтому
трое могут добавлять файлы, ни разу не отредактировав один и тот же.

### Ключ сессии

```python
Session(user_id, thread_id="default")
    .key    -> "u42:default"      # маршрутизация
    .scope  -> "user:u42"         # подо что кладётся память
SHARED = "shared"                 # видно агенту любого пользователя
```

Фильтр по скоупу применяется **до** ранжирования, а не после: чужой приватный факт не попадает
даже в сортировку.

### Конверт между агентами

```python
{"status": str, "result": dict | None, "needs_approval": bool}
```

Ветвимся по `status` из закрытого множества. Прозу друг у друга не парсим.

### `run_id`

Один ран проходит через loop 1 → loop 2 → куратора → лог → монитор под одним `run_id`. Это то,
по чему потом склеивается трейс.

### Запись в логе

```json
{"seq": 12, "at": "...Z", "kind": "handoff", "run_id": "u42-1729A-...",
 "payload": {...}, "prev": "<hash предыдущей>", "hash": "<sha256 этой>"}
```

`kind` из: `run_started`, `repair_verified`, `hint_delivered`, `handoff`, `fact_saved`,
`rule_added`, `note_written`, `notes_read`, `run_finished`. Неизвестный `kind` — исключение, а не
запись, которую монитор потом никогда не засэмплит.

## Слайс A — хранилища домена и сборка контекста

**Файлы:** `memory/sql.py`, `memory/rules.py`, `rules/tutor_rules.md`, `01_repair_loop.ipynb`
(+ исходник `scratch/nb1.py`), `traces/a_push_pull.md`, `docs/hw2-writeup-a.md`

### Что реализовано

- `state/memory.json` (`{"u42": {"off_by_one": 3}}`) заменён строками: `submissions`, `repairs`,
  `hints`. Счётчик, который там был, теперь один `GROUP BY`; те же строки дополнительно отвечают
  «на каких задачах, когда и что именно это было».
- `record_repair` отвергает тег не из энума и вызывается оркестратором **после** прохождения
  тестов, а не моделью. Первичный ключ `(run_id, mistake_tag)` — перезапуск ячейки не раздувает
  статистику, но два разных дефекта в одном ране считаются оба.
- Правила переехали из питоновской константы в `rules/tutor_rules.md` и читаются заново каждый
  ран: правка админом действует со следующего запуска, без рестарта.
- `build_context()` — push: правила → рекуррентные ошибки студента → потраченные подсказки.
  Порядок принципиален, правила байт-в-байт одинаковы для всех и держат кэшируемый префикс.
- В loop 1 добавлены два pull-тула: `retrieve_memory` и `read_problem_notes`. Модель зовёт их
  сама, и вызов виден в трейсе.
- Loop 1 отдаёт конверт `{status, result, needs_approval}` и пишет два файла: плоский
  `state/loop1_result.json` (его loop 2 парсит с HW1) и `state/loop1_envelope.json` для куратора.

### Как проверить

```bash
.venv/bin/python -m memory.sql        # 18
.venv/bin/python -m memory.rules      # 16
.venv/bin/python scratch/nb1.py       # 26, плюс живой прогон в конце
```

Или открыть `01_repair_loop.ipynb` и прогнать сверху вниз.

## Слайс B — мета-луп: куратор памяти

**Файлы:** `memory/db.py`, `memory/docs.py`, `memory/events.py`, `04_curator_loop.ipynb`
(+ `scratch/nb4.py`, `scratch/trace_b.py`), `rules/curator_brief.md`, `traces/b_curator.md`,
`docs/hw2-writeup-b.md`

### Что реализовано

- Документный стор: факты с `cue` (ключевые слова «когда это должно вернуться») и скоупом.
  Факт без cue стор **отвергает** — его всё равно никто никогда не достанет.
- Append-only лог с hash-chain: правка или удаление записи в середине ломает все хеши после неё,
  `verify_chain()` называет `seq`. Обрезание хвоста не ловится — это записано в докстринге рядом
  с проверкой, а не умолчано.
- Куратор — второй агент. Получает конверт исполнителя, сам решает, что запомнить. Три тула,
  бюджет четыре вызова, гейт человека на `propose_rule`, ран с ошибкой не учится вообще (ветка в
  коде до вызова модели).
- Координация через таблицу `handoffs` + лог, оба под одним `run_id`.

### Как проверить

```bash
.venv/bin/python -m memory.docs       # 21
.venv/bin/python -m memory.events     # 17
.venv/bin/python scratch/nb4.py       # 31, плюс два живых прогона
```

## Слайс C — shared/untrusted память и монитор

**Файлы:** `memory/notes.py`, `monitor.py`, `ask_tutor.py`, `05_monitor.ipynb`
(+ `scratch/nb5.py`, `scratch/trace_ac.py`), `docs/tool_descriptions.txt`,
`traces/c_shared_vs_private.md`, `traces/c_planted_comment.md`, `traces/c_monitor_report.md`,
`docs/hw2-writeup-c.md`

### Что реализовано

- Заметки студентов к задаче: A пишет, агент B читает. `risk` и `flagged` считаются **на
  записи**, чтобы читатель не мог их пропустить. Высокий риск запись не блокирует — фильтр на
  входе только учит атакующего, какая формулировка проходит.
- `read_problem_notes` возвращает не голый текст, а конверт: банер «это данные, а не
  инструкции», `author`, `trust="untrusted"` и флаги сканера.
- `ask_tutor.py` — минимальный путь «студент спросил → агент ответил». Ни один из трёх циклов не
  является вопросом студента, а «A написал заметку, агент B её прочитал» требует именно этого.
- `monitor.py` — судья на своих часах над hash-chained логом. Именованные значения вместо
  оценок 1–10, обязательный `rationale` (expected против got), буква оценки выводится из
  значений. Нечитаемый судья → ран `unjudged`, а не «чисто». Сломанный лог → не грейдится вообще.
- Второй режим монитора: чтение всего набора инструкций на противоречия.

### Как проверить

```bash
.venv/bin/python -m memory.notes      # 28
.venv/bin/python scratch/nb5.py       # 28, плюс живой отчёт
.venv/bin/python monitor.py --since 0 --sample 8    # только с API-ключом
```

## Что осталось незакрытым, и это честно написано в отчётах

- Бюджет в три подсказки — строка в `tutor_rules.md`, которую модель может проигнорировать;
  `hints_spent()` есть, но в коде он не форсится.
- Подсказка пишется в SQLite вызывающей стороной, а не самим loop 2 — иначе 22 теста loop 2
  начали бы писать в настоящую базу на каждом прогоне. Шов виден в докстринге `sql.record_hint`.
- Правила инжекций англоязычные, а студенты пишут по-русски. Это же ограничение уже записано в
  `03_prompt_shield.ipynb`.
- Точность судьи проверена только на кейсах, которые мы сами написали.

## Где реально можно столкнуться

- **`memory/db.py`** — единственный файл, который нужен всем трём. Приземляется в коммите B.
- **Один ноутбук — один владелец.** Ноутбуки в git это JSON, мерж-конфликты в них разбирать
  больно. `02_hint_loop.ipynb` и `03_prompt_shield.ipynb` не трогает никто.
- Правишь `.py` в `scratch/` — пересобирай ноутбук через `scratch/py2nb.py`, а не редактируй
  JSON руками.
- **`state/`** в `.gitignore`, поэтому трейсы лежат в **`traces/`**.
